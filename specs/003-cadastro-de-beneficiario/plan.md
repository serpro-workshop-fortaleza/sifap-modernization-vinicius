## Decisões de projeto

### O agregado é o beneficiário, e o dependente vive dentro dele

O [ADR-0004](../../docs/adr/0004-mapeamento-dependentes-jpa.md) já decidiu `@OneToMany` com entidade `Dependent` própria. O que o plano acrescenta é a fronteira transacional: **dependente não é raiz de agregado**. Toda operação sobre dependentes passa por `Beneficiary`, que é quem conhece o limite de seis ativos e quem verifica duplicidade.

Consequência direta sobre o `REQ-BEN-009` e o `REQ-BEN-012`: a contagem de ativos é um método do agregado, e a verificação de duplicidade percorre a coleção carregada. O defeito legado — percorrer um contador que pode estar defasado (`CADDEPEN.NSP:176`) — não tem como se repetir, porque não existe contador.

```java
public int activeDependentCount() {
    return (int) dependents.stream().filter(Dependent::isActive).count();
}
```

### Situação cadastral fora do comando de alteração

O [ADR-0006](../../docs/adr/0006-situacao-cadastral-do-beneficiario.md) decidiu que alteração cadastral não toca situação. A tradução em código é que `UpdateBeneficiaryCommand` **não possui campo de situação**.

Isso é mais forte do que validar: não existe caminho para o valor chegar. É a mesma técnica dos value objects `Cpf` e `Nis` da Fatia 1 — a garantia vem da forma do tipo, não da disciplina de quem chama.

Mudar situação é `ChangeBeneficiaryStatusCommand`, com motivo obrigatório.

### Validação bloqueante, e uma única vez

O `REQ-BEN-003` corrige o padrão que organiza toda esta fatia: validar e ignorar o resultado. A tradução é que a validação acontece **na construção do agregado**, não antes dele.

| Legado | Sistema novo |
|---|---|
| `CADBENEF.NSP:151` valida com rotina interna | Kernel `DocumentValidator`, rotina única |
| `:161` chama `SUBVALCP` e ignora o retorno | Não há segunda chamada |
| `:263` chama `VALBENEF` e escreve aviso | Falha de validação impede a construção |

Um `Beneficiary` existente é um beneficiário válido. A regra do `AC-003.3` — não validar duas vezes o mesmo dado — sai de graça.

### Sinalização de carga não é situação cadastral

O `REQ-BEN-020` exige migrar registros inválidos sinalizados. A tentação é criar um valor de situação `PENDENTE`, e isso seria um erro: contaminaria o domínio de negócio com um estado que só existe por causa da migração, e o `VALELEG` da Fatia 4 teria de conhecê-lo.

**Decisão:** tabela separada `beneficiary_migration_issue`, com o CPF, o motivo e o valor original recusado. O domínio permanece com os cinco valores do dicionário.

Registro migrado com pendência mantém a situação que tinha na origem. Quando a origem estava em branco, a situação fica **nula** e o registro é sinalizado — nenhuma atribuição automática, conforme o aviso do ADR-0006.

> A coluna `status` é anulável **apenas** para registros migrados. Registros criados pelo sistema novo têm situação obrigatória, garantida na construção do agregado. A restrição de banco distingue os dois casos pela presença de pendência de migração.

### A carga lê extração, não o Adabas

Não há conectividade com o mainframe, e o `FDT-150-BENEFICIARY.txt` estima 90 minutos para descarga completa. A carga consome um **arquivo de extração posicional**, produzido pela operação, e não conversa com o Adabas.

Consequência para o `REQ-BEN-021`: a carga é o primeiro momento em que se conhece o domínio real dos dados. O inventário de valores encontrados é saída obrigatória, não opcional.

### Controle de concorrência que o dicionário já previa

`BENEFIC.ddm:118` declara `GG NUM-VERSION N 5 CONCURRENCY CONTROL` e nenhum programa o utiliza. O `CADBENEF` faz `FIND` e `UPDATE` sem qualquer proteção (`:306-320`): duas sessões alterando o mesmo beneficiário sobrescrevem-se em silêncio.

**Decisão:** `@Version`. É o uso do campo que o legado declarou e nunca ligou, e o custo é uma anotação.

### Endereço como objeto de valor completo

O `REQ-BEN-018` proíbe truncar. O legado grava 80 caracteres em um campo de 60 (`CADBENEF.NSP:277-279`), e o próprio dicionário já separa logradouro, número e complemento (`BENEFIC.ddm:57-67`), campos que o programa nem oferece na tela.

`Address` vira `@Embeddable` com a estrutura do dicionário, e a interface captura os campos que existem.

## Modelo de dados

```sql
CREATE TABLE beneficiary (
    id                BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    cpf               VARCHAR(11)  NOT NULL UNIQUE,
    nis               VARCHAR(11)  UNIQUE,
    full_name         VARCHAR(60)  NOT NULL,
    birth_date        DATE         NOT NULL,
    sex               VARCHAR(1)   NOT NULL,
    status            VARCHAR(12),
    status_reason     VARCHAR(60),
    status_changed_at TIMESTAMPTZ,
    program_code      VARCHAR(4),
    family_income     NUMERIC(11,2),
    -- endereço, sem truncamento
    street            VARCHAR(120),
    street_number     VARCHAR(10),
    complement        VARCHAR(30),
    district          VARCHAR(40),
    city              VARCHAR(40),
    uf                VARCHAR(2),
    postal_code       VARCHAR(8),
    region_code       VARCHAR(2),
    phone_mobile      VARCHAR(15),
    rg_number         VARCHAR(15),
    registered_at     DATE         NOT NULL,
    created_at        TIMESTAMPTZ  NOT NULL,
    created_by        VARCHAR(50)  NOT NULL,
    updated_at        TIMESTAMPTZ  NOT NULL,
    updated_by        VARCHAR(50)  NOT NULL,
    version           BIGINT       NOT NULL DEFAULT 0,
    CONSTRAINT ck_beneficiary_status CHECK (
        status IN ('ATIVO','SUSPENSO','CANCELADO','INATIVO','DESLIGADO')
    ),
    CONSTRAINT ck_beneficiary_sex CHECK (sex IN ('M','F','I'))
);

CREATE TABLE dependent (
    id             BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    beneficiary_id BIGINT       NOT NULL REFERENCES beneficiary(id),
    cpf            VARCHAR(11),
    full_name      VARCHAR(60)  NOT NULL,
    birth_date     DATE,
    relation       VARCHAR(2)   NOT NULL,
    status         VARCHAR(12)  NOT NULL,
    disability     BOOLEAN      NOT NULL DEFAULT FALSE,
    CONSTRAINT ck_dependent_status CHECK (status IN ('ATIVO','INATIVO','DESLIGADO')),
    CONSTRAINT uq_dependent_cpf UNIQUE (beneficiary_id, cpf)
);

CREATE TABLE beneficiary_migration_issue (
    id             BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    beneficiary_id BIGINT       REFERENCES beneficiary(id),
    source_cpf     VARCHAR(20)  NOT NULL,
    issue_type     VARCHAR(40)  NOT NULL,
    field_name     VARCHAR(40),
    original_value VARCHAR(120),
    detected_at    TIMESTAMPTZ  NOT NULL
);
```

`uq_dependent_cpf` é a garantia do `REQ-BEN-012` no banco. Como o PostgreSQL não considera `NULL` igual a `NULL`, vários dependentes sem CPF convivem sem colisão — que é exatamente o `REQ-BEN-011`, sem precisar do valor sentinela de onze zeros.

### Índices

```sql
CREATE INDEX idx_beneficiary_uf_status ON beneficiary (uf, status);
CREATE INDEX idx_beneficiary_program_status ON beneficiary (program_code, status);
CREATE INDEX idx_beneficiary_birth_year ON beneficiary (EXTRACT(YEAR FROM birth_date));
```

Os dois primeiros são os equivalentes de `S2 SUPER-UF-STAT` e `S3 SUPER-PROG-STAT`; o terceiro corresponde ao subdescritor `SA YEAR-BIRTH`. O dicionário indica quais consultas o sistema realmente faz, e é a melhor fonte disponível de padrão de acesso.

O hiperdescritor `H1 HYPER-BAND-ELIG` fica de fora: seu código está em Assembler, ausente do acervo (`SIFAP-M-...`), e o consumidor é a Fatia 4.

## Contrato do módulo

### Interface pública

```java
public interface BeneficiaryQuery {
    Optional<BeneficiaryView> findByCpf(Cpf cpf, Actor actor);
    Optional<BeneficiaryView> findByNis(Nis nis, Actor actor);
}
```

O `Actor` é parâmetro obrigatório da consulta porque o `REQ-BEN-016` exige registrar quem acessou. Sem ele no contrato, o registro dependeria de o chamador lembrar — o padrão que a Fatia 1 eliminou da auditoria.

### API REST

Substitui as telas 3270 do `CADBENEF`, `CADDEPEN` e `CONSBENF`.

| Método | Caminho | Requisitos |
|---|---|---|
| `POST` | `/api/v1/beneficiaries` | `REQ-BEN-001`, `002`, `003` |
| `PUT` | `/api/v1/beneficiaries/{cpf}` | `REQ-BEN-005`, `018` |
| `POST` | `/api/v1/beneficiaries/{cpf}/status` | `REQ-BEN-004`, `006` |
| `POST` | `/api/v1/beneficiaries/{cpf}/dependents` | `REQ-BEN-008`, `010`–`014` |
| `GET` | `/api/v1/beneficiaries/{cpf}` | `REQ-BEN-015`, `016`, `017` |
| `GET` | `/api/v1/beneficiaries?nis={nis}` | `REQ-BEN-015` |

### Eventos publicados

Confirmam o catálogo provisório de [`domain-events.md`](../../02-modern-spec/domain-events.md), sem alteração de forma.

| Evento | Ação de auditoria | Requisito |
|---|---|---|
| `BeneficiaryRegistered` | `INCLUSAO` | `REQ-AUD-001` |
| `BeneficiaryUpdated` | `ALTERACAO` | `REQ-AUD-006` |
| `BeneficiaryStatusChanged` | `ALTERACAO` | `REQ-BEN-006` |
| `DependentAdded` | `ALTERACAO` | `REQ-AUD-001` |
| `BeneficiaryQueried` | `CONSULTA` | `REQ-BEN-016` |

Todos implementam `AuditableEvent`, já consumido e testado pela Fatia 1. O contexto não conhece o módulo de auditoria.

## Estratégia de testes

| Requisito | Verificação |
|---|---|
| `REQ-BEN-003` | Teste que prova que documento inválido impede a construção do agregado |
| `REQ-BEN-005` | Teste de caracterização invertido: alteração cadastral **não** altera situação |
| `REQ-BEN-008` | Teste de borda em cinco e em seis dependentes ativos |
| `REQ-BEN-009` | Inativar dependente reduz a contagem sem escrita adicional |
| `REQ-BEN-011` | Dois dependentes sem CPF no mesmo titular, contra restrição real do PostgreSQL |
| `REQ-BEN-012` | Duplicidade barrada pelo banco, não apenas pela aplicação |
| `REQ-BEN-016` | Consulta gera evento na trilha de acesso, e não na de alteração |
| `REQ-BEN-018` | Endereço de 120 caracteres volta íntegro da base |
| `REQ-BEN-020` | Carga com registro inválido produz beneficiário migrado e pendência registrada |
| `REQ-BEN-021` | Carga com valor de parentesco fora do domínio produz linha de inventário |

### Testes de divergência deliberada

Dez requisitos são nível `C`. Cada um recebe um teste que cita o membro legado cujo comportamento deixa de ser reproduzido, no formato adotado em `LegacyDivergenceTest` na Fatia 1.

O mais importante:

```java
// REQ-BEN-005, nivel C. CADBENEF.NSP:314 grava branco sobre a situacao vigente,
// e VALELEG.NSN:133-151 trata branco como elegivel: alterar o endereco de um
// beneficiario suspenso o reativa em silencio.
@Test
void deve_preservar_a_suspensao_quando_dados_cadastrais_sao_alterados() { ... }
```

### Limitação de caracterização

A mesma da Fatia 1, e vale repetir: **não há ambiente legado disponível**. Os vetores derivam da leitura do código. Se o acesso for obtido, os casos de borda de `REQ-BEN-007` — idade calculada por ano civil — devem ser reconfirmados antes da carga.

## Riscos

| Risco | Impacto | Mitigação |
|---|---|---|
| Volume de registros com situação em branco pode ser muito alto | A carga pode produzir mais pendências do que registros limpos | `REQ-BEN-021` mede antes; a decisão sobre o destino é de negócio |
| Domínio real de parentesco é desconhecido | O enum pode não comportar os valores existentes | A carga inventaria e sinaliza; não recusa |
| Validação bloqueante recusa registros hoje aceitos | Beneficiário pode ficar sem cadastro utilizável | `REQ-BEN-020` proíbe descarte; registro migra sinalizado |
| Carga de 4,2 milhões de registros com dependentes expandidos | Janela de migração | Inserção em lote, mesma técnica medida na `T-110` da Fatia 1 |
| `REQ-BEN-007` preserva um cálculo de idade defeituoso | Suspensões em data errada continuam | Nível `PS`: o evento registra data de nascimento e idade apurada, tornando o efeito mensurável |
